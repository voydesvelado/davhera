The Portfolio Build

Real on top,
thin underneath.

A scope for the portfolio-grade version of the booking product. Production-quality frontend, persistence via Supabase free tier, zero outbound costs. Buildable in two focused weeks.

Section I

Build philosophy.

A clickable demo is a screenshot. A working demo is a product. The difference matters more for the portfolio than the actual product matters for the user.

The goal is to ship something a hiring manager can play with end-to-end and leave thinking this person can build the entire thing. The principle is to make everything that touches the visitor feel completely real, and to fake only the parts a visitor would never see anyway — outbound notifications, payments, account creation.

The portfolio piece is not a prototype of the product. It is the product, minus the parts that cost money.

What this gets you

A live URL where any reviewer can be either a doctor (seeing her dashboard, today's appointments, the onboarding flow) or a patient (browsing Dra. Sofía's profile, picking a time, booking, getting a tokenized confirmation, returning later to reschedule). Their state persists because Supabase is real. Nothing they do affects another visitor's experience because every session is scoped to its own cookie.

It also gets you a design system documented in code, an obvious "Direct Design" exhibit, and a project that maps cleanly onto the Lumina-tier role descriptions you have been preparing for.

Section III

The demo mode mechanic.

Every visitor lands on the same content but each gets their own state, so they can play without colliding with each other or affecting Dra. Sofía's seeded data.

Session identity

On first visit, an anonymous session ID is set in a cookie. Every booking created during that visit is tagged with the session ID. The visitor can reschedule and cancel their own bookings only; Sofía's seeded bookings are read-only.

What persists, what doesn't

Bookings persist for 30 days then auto-expire via a Supabase scheduled function. Slots taken by one visitor's bookings remain unavailable to other visitors until the booking is cancelled or expires — which makes the conflict-prevention story visible and real.

The ribbon

A small persistent indicator in the corner: Demo · concepto. Tappable, opens a sheet explaining what is real and what is faked. This protects against any confusion if the URL is shared and it doubles as a design-thinking exhibit.

Mode picker

The marketing site has two CTAs alongside the standard ones: Ver el producto como doctora and Ver el producto como paciente. The reviewer can context-switch between the two sides without losing their state.

Section V

Data model.

Lean. Five tables. Everything Sofía-related is seeded once; everything visitor-created is scoped to a session.

slug text unique — dra-sofia-ramirez
name text
specialty text
bio text

id uuid pk

id uuid pk

bookings
id uuid pk
token text unique — for tokenized links
doctor_id uuid fk
service_id uuid fk
starts_at timestamptz
ends_at timestamptz
patient_name text
patient_phone text
patient_email text
patient_note text nullable
status text — confirmed / cancelled / completed
demo_session_id text — scopes to visitor cookie
created_at timestamptz default now()
expires_at timestamptz — 30 days, for cleanup
UNIQUE (doctor_id, starts_at) WHERE status = 'confirmed'

Slot generation happens client-side from availability_rules minus existing bookings minus blocked_periods. No slots table — slots are derived, not stored. This is the right pattern and the same one used by every calendar product worth modeling.

Row Level Security

RLS on bookings: visitors can read/write only rows where demo_session_id matches their cookie. Sofía's seeded bookings are readable by all (so the calendar feels populated) but writable by none. Two policies, both short.

Section VII

Build sequence.

Two weeks of focused build. Each "week" is roughly 30–40 hours; compressible if you go hard, expandable if other obligations interrupt.

Day 1
Foundation
Next.js + TS + Tailwind + Framer Motion project setup. Supabase project, schema, seed Sofía's profile, services, availability. RLS policies. Cookie-based session middleware. Deploy first version to Vercel with a placeholder homepage. The pipeline is now real.
Day 2–3
Design system
Type scale, color tokens, spacing, motion primitives. Build the foundation components (Button, Input, Sheet, Toast, Badge). Stand up /sistema as the living style guide. Every later screen pulls from this.
Day 4–6
Public profile + booking flow
The hero asset. /dra-sofia-ramirez, the booking sheet, slot generation logic, confirmation page, tokenized reschedule and cancel. The WhatsAppPreview component. End of day six: a visitor can book Sofía and the booking persists.
Day 7–9
Doctor dashboard
Today view, week calendar, availability editor, services editor, block-time sheet, the "próximos recordatorios" showcase screen. Profile editor. End of day nine: the doctor side is complete.
Day 10–11
Onboarding flow
The 2-minute /registro sequence. Six screens that feel like one continuous gesture. Doesn't actually create a doctor — culminates in a "your page is live" screen that links to the seeded Sofía profile. This is one of the most-watched flows for a reviewer; design it carefully.
Day 12–13
Marketing site
Landing page, manifesto, mode picker, demo ribbon. The editorial-neutral aesthetic at full strength. Drop the research documents in as deep links from the manifesto for the curious reviewer.
Day 14
Polish, motion, edge cases
Loading states. Empty states. Error states. Mobile spot-checks. Slot-taken-mid-flow handling. Animations between screens. Open Graph images. Favicon. The 24-hour pass that turns a build into a portfolio piece.
Section VIII

Portfolio framing.

The build is only half of the value. How you present it determines whether reviewers see a "design exploration" or a "design engineer who can ship product." Two things make the difference.

The case study page

A dedicated long-form page on your portfolio site that links to the live demo, walks through the research and decisions, and embeds key screens. The four research documents in this series become the substance of that page — they show the strategic layer beneath the visual one. Reviewers spend more time on case studies that demonstrate thinking than on Dribbble shots.

The opening line

Lead with the right framing. Something close to:

A working concept product for Mexico's independent healthcare professionals — researched, designed, and built end-to-end in code. Two-week solo build.

"Concept product" is honest — it isn't live with paying customers. "Working" is also honest — every flow functions. "Researched, designed, and built end-to-end in code" is your positioning as a design engineer, written in one sentence.

The technical artifacts that matter

Link the Supabase schema, the component inventory, the design system page. These are not Dribbble assets — they are evidence. The role you are targeting wants to see the system, not the screenshot.

Two weeks of focused work for a portfolio asset that maps to the exact role you are aiming for — and a fully-formed product you can decide to turn real if the demand signal arrives.

Whichever way that goes, the cost is the same.
